# AdvisePoint Docs v1.3.0 candidate 3 verification

September 20, 2026. Local testing only; not a final release. No GitHub publication, enabled updates, automatic migration or library deletion. This candidate preserves candidate 2's upload logging and rendered-page fallback, plus the v1.2.8 updater implementation.

## Printing behavior

- Retained PDFs no longer have a 20-page print cap. Small selections keep the bounded image preview. Larger selections use PDF handoff.
- Full manuals reuse the original bytes. Unrestricted subsets use a dedicated cancellable worker. Protected subsets preserve the original security and explicitly instruct the user to select the requested original page range.
- A one-minute soft warning allows continued preparation, cancellation or a user-requested PC PDF app handoff. Preparation stops at two minutes; errors and resource limits also offer the original-file route.
- Subset-copy input and output are limited to 128 MiB. This is not a guarantee that total parser memory stays below 128 MiB.
- No automatic opening or printing. The existing protected Windows open-original route is used only after a click. Browser/native-reader processing after handoff is not monitored by the preparation timer.
- Existing rendered-page printing is unchanged; those documents have no retained original.

## Functional results

292 passing automated checks: 269 regression/unit/browser/reset/logging, 13 retained-PDF and isolation, seven large-print checks, three fallback workflow checks. Initial backup-test failures due to a full sandbox disk were rerun after removing disposable test data; all 13 integration checks then passed. No user library was used.

Large-print checks cover a 120-page whole document, a 31-page subset with text/page dimensions/rotation verified, security restrictions, cancellation/retry, two-minute stop, actual Chromium PDF tabs, and the one-minute explicit-only PC-app request. The Windows launch itself is stubbed in browser automation and remains a hardware acceptance item.

The three supplied manuals have 793, 770 and 791 pages. Full-manual handoff preserved original hashes and took 373, 341 and 369 milliseconds of in-app preparation respectively in the measured run. These are not full browser print-preview, printer-spooling or physical-print times.

## Responsiveness gate: FAIL, release hold

A full 724-page fallback import was run while viewing another retained manual. Every page completed, search remained successful and health checks stayed successful. The investigation threshold failed because a large original took more than 30 seconds to transfer while rendering was active.

| Phase | Search | First visible page | Jump to page 700 | Complete original delivery |
|---|---:|---:|---:|---:|
| Idle | 113 ms | 3,922 ms | 867 ms | 462 ms |
| Early active rendering | 751 ms | 6,380 ms | 6,182 ms | 37,864 ms |
| Later active rendering | 236 ms | 5,561 ms | 3,570 ms | 12,559 ms |
| After rendering | 262 ms | 692 ms | 725 ms | 532 ms |

These are single-run Linux sandbox/Chromium measurements, not a benchmark of either Windows architecture. Original delivery is HTTP transfer, not Windows file-association launch. They demonstrate contention during fallback rendering but do not establish that the user's report has an x64-specific cause. No renderer-isolation fix is included in candidate 3. Resolve the contention and repeat Windows x64/ARM64 measurements before final release.

## Security and known limitations

The September 20 npm audit reports zero findings. Runtime modules remain the baseline set; Node remains 20.18.1. An npm audit is not certification of every bundled binary. No new dependency was added; the worker bundles the already-locked pdf-lib dependency.

TypeScript checking still reports the same 14 pre-existing diagnostics in LibraryScanPanel, backup-scheduler and locate. No new diagnostics appear in the changed printing files. Windows execution, external PDF reader behavior, actual printer processing, Chrome/Edge overnight behavior and final user acceptance remain pending.
